# Векторный индекс — отложено до роста корпуса

**Статус:** deferred. Сейчас осознанно остаёмся на «файлы + manifest для топиков». Этот документ — capture идеи на момент когда корпус Auto-Wiki вырастет настолько что file-based recall начнёт пропускать связи.

## Когда возвращаться

Триггеры для пересмотра:

- [ ] entity-страниц больше ~200 (сейчас ~25)
- [ ] grep-based `/topic` auto-discovery начнёт регулярно пропускать релевантные сущности (например, на запрос `health` не найдёт `ramus`/`psoriasin`/`_father` потому что слово «health» в них не встречается явно)
- [ ] `recall` начнёт давать ложно-отрицательные ответы («не помню») на запросы про вещи которые в вики ЕСТЬ но описаны другими словами
- [ ] wholesale-read entity descriptions (текущий fallback) перестанет влезать в контекст одного LLM-вызова

Любой один трек уже повод подумать; два сразу — повод делать.

## Почему текущий SPEC отказался от векторов

См. CLAUDE.md «Anti-patterns». Запрет был против доминирующего паттерна того времени: **cloud vector DB (Pinecone, Weaviate) + cloud embeddings (OpenAI ada-002)**. Этот паттерн ломает Ginarr-философию: vendor-coupling, runtime-зависимость от внешних сервисов, embedded-данные живут не в твоём vault'е.

Запрет был корректный для того что имелось в виду. Но он не охватывает локальный self-hosted сетап, который технически совместим с file-based концепцией.

## Что будет когда придёт время

Локальный embedding-стек, vendor-neutral по той же логике что и сама Ginarr:

- [ ] **Embedding модель:** BGE-small (`BAAI/bge-small-en` или multilingual-e5-small) — быстро на 3090 владельца, открытая, заменимая
- [ ] **Vector store:** `sqlite-vec` extension. Векторы живут в обычном sqlite-файле в `Auto-Wiki/_vectors/index.db`. Это **тоже плоский файл в vault'е** — переживает миграции, читается любым клиентом со sqlite
- [ ] **Регенерация:** cron `reindex-vectors.sh` после `ingest-and-weave`, в `00:35 UTC`. Полный rebuild на каждом проходе пока корпус маленький; incremental update когда станет больше
- [ ] **Использование как secondary index:** векторы НЕ source of truth. Markdown-файлы остаются каноническими. ANN-поиск только расширяет recall в `/topic` auto-discovery и `recall`-запросах:
  1. Грепаешь по точным словам (узкий exact recall)
  2. ANN по embedding запроса → топ-N семантически близких entity-страниц
  3. Объединение → LLM фильтрует
- [ ] **Index lag окно** компенсируется тем что свежие факты (последние ~24h) точно есть в дневном JSONL-логе, который индексировать не надо — греп всегда актуален

## Какие проблемы это решает

- Семантическая близость без синонимных таблиц: запрос `health` находит `fitness`, `medical`, `симптомы`, `врач`, etc. без явного описания связей
- Recall-completeness на больших корпусах когда wholesale-read больше не помещается в контекст
- Auto-discovery в `/topic <new-name>` начинает работать осмысленно для тем которых заранее не предусмотрел

## Какие новые tradeoffs появляются

- **Embedding model lock-in.** Сменишь модель — все индексы перестроить с нуля. План миграции: пересборка через cron в одну ночь, downtime ~часы. Не страшно.
- **Approximate retrieval.** Векторы хороши для recall, плохи для precision. Точечные запросы («что я сказал про Эли вчера») всё равно должны идти через греп, не через ANN.
- **Index lag.** Между записью факта и переиндексацией есть окно где факт невидим для семантики. Минимизируется частым cron'ом + fallback на сырые логи для свежих фактов.
- **Дополнительная зависимость:** Python + sentence-transformers + sqlite-vec. Новая поверхность для багов.

## Где сейчас лежат «заплатки»

До векторов проблему recall-completeness частично закрывают:

- `lint-indexes` обеспечивает что у каждого файла есть осмысленное описание (LLM-fallback если автор не написал) — это база для семантического матчинга через LLM-as-semantic-layer
- Manually curated манифесты в `wiki/topics/<name>.md` — точный exact-match для известных тем
- `lint-wiki` flag на entities без описаний — будущий чек-лист «починить описания» как инвестиция в recall до того как векторы понадобятся

Когда эти заплатки начнут протекать — открывать этот документ.
